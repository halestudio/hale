# hale»studio on hale-core

This document records how hale»studio is built on hale-core, why, and which alternatives were
rejected.

## Context

The headless parts of hale (common, cst, io, util, app) moved to the separate repository hale-core.
hale-core is a plain Java library. It is released to the wetransform Artifactory together with a BOM,
and other projects use it without OSGi.

hale»studio is an Eclipse RCP application and needs all its libraries as OSGi bundles in a target
platform. Before, it got its third-party libraries from a prebuilt p2 site in the repository
hale-build-support, which was committed as binaries and referenced by a fixed commit in the target
definition, and it built the hale-core modules from source copies in this repository.

Goal: build hale»studio on released hale-core artifacts, so that

- the library versions are exactly those of the hale-core BOM;
- there are no source copies of the hale-core modules in this repository;
- a dependency update in hale-core reaches hale»studio by changing a single version.

## Decisions

### Generate the target platform with bnd-platform from the hale-core BOM

The platform is generated by `build/platform` (Gradle with the plugin `org.standardout:bnd-platform`).
It resolves the hale-core features and bundles plus the libraries that only hale»studio uses, with
the hale-core BOM as constraints. It wraps everything as OSGi bundles where needed and publishes a p2
update site. It also generates `platform/local-platform.target`, which consists of the locations of
`platform/base-platform.target` (Eclipse and other p2 repositories) and a location with the update
site.

**Rejected alternative: Tycho Maven target locations** with `missingManifest="generate"`, where Tycho
wraps the jars itself during target resolution.

| | Generated platform (chosen) | Tycho Maven locations |
|---|---|---|
| Version alignment | Gradle applies the BOM constraints to the whole dependency graph | Maven "nearest wins"; aligning with the BOM needs many versioned `<exclude>`s, which silently stop matching after a version update |
| OSGi fixes | targeted per library (optional imports, exports, merged bundles, SPI headers) | one template for all wrapped jars, e.g. `Import-Package: *;resolution:=optional` and `DynamicImport-Package: *`, which hides missing packages until runtime |
| Build cost | separate generation step and an Eclipse for the p2 publisher (see below) | none beyond Tycho resolution |

The build costs are reduced by skipping the generation if its inputs did not change and by caching
the platform in CI.

### Generate the platform in this repository

- **Not in hale-core.** hale-core is meant to be a lean library without OSGi. For every downstream
  user except hale»studio, a p2 site, SPI Fly or an Eclipse publisher would only be ballast.
- **Not as a separately published artifact** (as with hale-build-support). Every dependency update or
  OSGi fix would need a round trip through another repository and a publish step before hale»studio
  could use it.

Dependencies and platform fixes therefore change in one PR in this repository.

### Use released hale-core versions only

The platform is generated from a hale-core release (`haleCoreVersion` in
`build/platform/build.gradle`). Snapshots can be used to try unreleased hale-core changes, but are
not merged.

### Work around hale-core issues in the platform

Some hale-core bundles do not resolve or load in OSGi. The platform build fixes their manifests (see
the section "Workarounds for hale-core bundles" in `build/platform/build.gradle`).

A fix moves to hale-core only if it is relevant for all users of hale-core, most of which use it
without OSGi. It needs a test in hale-core that shows the problem in that setting. Problems that only
occur in OSGi, such as packages that are only referenced in plugin.xml or classes compiled by Groovy
at runtime, stay fixed here.

### SPI Fly for ServiceLoader lookups, configured per library

Current versions of hale-core's dependencies find their implementations through
`java.util.ServiceLoader`, e.g. SLF4J 2 finds logback, jakarta.xml.bind finds the JAXB runtime and
eclipse-collections finds its factories. In OSGi a bundle cannot see the `META-INF/services` of
other bundles.

- Aries SPI Fly (OSGi Service Loader Mediator) is part of the platform and has to run at start level 1.
- Only the bundles that need it get `SPI-Consumer`. The providers get `SPI-Provider` and lazy
  activation, because SPI Fly only registers the providers of started bundles.
- The lists are `spiConsumers` and `spiProviders` in `build/platform/build.gradle`, and the merged
  GeoTools bundle in `build/platform/modules/geotools.gradle`.
- Rejected: `SPI-Provider/Consumer: *` on every wrapped jar.

### Pin the Eclipse used by the p2 publisher

bnd-platform publishes the update site with an Eclipse from its downloads directory. It uses whatever
it finds there, without checking the version, and an older Eclipse can silently drop bundles from the
update site. The platform build therefore uses a pinned Eclipse release (`eclipseMirror`) in a
directory of its own.

The publisher Eclipse does not have to be the release of the target platform. It stays at 2023-09,
which runs on Java 21 and is available from archive.eclipse.org; current releases are only on
download.eclipse.org, where they are removed later.

### Skip the generation if its inputs did not change

`generatePlatform` only regenerates the platform if its inputs changed. The fingerprint is stored in
`build/platform/build/platform-fingerprint.txt` and covers:

- the files under `build/platform` and `platform/base-platform.target`;
- the bnd-platform plugin with its dependencies, so a locally built bnd-platform (`-PbndPlatformVersion`)
  triggers a regeneration;
- the resolved dependencies, with the unique version of snapshots;
- the location of the update site, which the generated target refers to by its absolute path.

The check only needs the dependency metadata, not the artifacts. `-PforceGeneratePlatform` forces the
generation. Gradle checks for new snapshots once a day; use `--refresh-dependencies` to get a hale-core
snapshot that was published in the meantime.

**CI** restores the platform from the GitHub Actions cache before the build and saves it afterwards
(composite actions `.github/actions/restore-platform` and `.github/actions/save-platform`):

- The most recent entry for the OS is restored. The fingerprint check of the build decides whether
  it can be used.
- A platform is only saved if it was generated in that run. The cache key is derived from the
  fingerprint.
- The archive of the publisher Eclipse is cached separately. Its key contains the Eclipse release and
  has to be changed together with `eclipseMirror`.

### Eclipse 2026-09, Java 21 and Tycho 5

hale»studio runs on the current Eclipse release, 2026-09 (4.41), instead of 2020-03 (4.15). Eclipse
requires Java 21, so the build, CI and the products use Java 21:

- **Build:** Tycho 5 (requires Maven 3.9.9 or later, so the embedded Maven of `build/buildSrc` is
  3.9) and the JDK from `mise.toml`. The groovy-eclipse compiler of Groovy 2.5 works on Java 21, but
  runs in a separate process, and the Groovy-compiled bundles stay at Java 15 byte code.
- **Manifests:** all bundles require `JavaSE-21`. Tycho resolves the dependencies of a bundle with the
  constraints of its execution environment, and the Eclipse bundles require Java 21.
- **JREs:** Eclipse Temurin 21 JREs are downloaded directly from Adoptium (GitHub releases), not from
  the artifacts mirror in hale-build-support. The downloads are checked against the SHA-256
  checksums in `artifactChecksums` (`build/build.gradle`); update them together with the URLs (the
  Adoptium API lists them).
- **Target:** the Eclipse units come directly from `https://download.eclipse.org/releases/2026-09/`.
  The locations use the slicer, which follows feature inclusions, but neither package and bundle
  requirements nor requirements with version ranges. The libraries required by the Eclipse bundles
  are therefore listed explicitly in `platform/base-platform.target`, each with a comment why. All
  locations include all platforms (Tycho requires the same value for all of them), so that units
  restricted to Windows can be listed.
- **GEF Classic** replaces GEF legacy 3.11 and the unreleased Zest 2 snapshot of 2012. Its Zest has
  the Zest 2 API. The DOT export of Zest 2 is not part of it; hale»studio writes DOT itself
  (`DotWriter` in `ui.util.graph`).
- **Help system:** Jetty 12 (ee8, javax.servlet 4), the Apache JSP of Mortbay and Lucene 10 replace
  Jetty 8, Glassfish Jasper and Lucene 8. The servlets of the help web application are Declarative
  Services components, so every product with help (including the Infocenter) has to start
  `org.apache.felix.scr`.
- **Removed:** the live editor feature (e4 model editor), which was part of no product and would have
  needed PDE with bnd and bndtools in the target.

### Remove unused and unmaintained parts

Building on hale-core is a breaking change anyway, so parts that were not built or not maintained
any more were removed: the FME integration (its bundles only existed in the old platform), the
AGeoBw extension (only shipped by its own product definition) and bundles that were excluded from
the build.

### Version 6.0.0

All bundles, features and products have the same version, 6.0.0. `setSnapshotVersion
-PnewVersion=…` sets a given version (`setSnapshot` can only increase the minor version).

### Test in OSGi: feature-based test product and smoke test

hale-core tests its bundles on a flat class path, so it cannot see problems that only occur in OSGi:
unresolved bundles, packages exported by two bundles, ServiceLoader lookups across bundles, classes
only named in plugin.xml and Groovy compiled at runtime that cannot see the Groovy runtime.

- **Test product** (`ui/plugins/eu.esdihumboldt.hale.ui.application/Tests.product`): feature based
  like `HALE.product`. It contains the hale»studio features, the platform feature and
  `eu.esdihumboldt.hale.ui.feature.tests` with the test fragments of this repository, JUnit and the
  Equinox test runner.
- **Smoke test** (`build/gradle/smokeTest.gradle`): part of `commitStage`, runs on the test
  product. It starts the product without UI, checks that all bundles resolve (Equinox console `ss`)
  and runs headless transformations of two sample projects of the user documentation: the Groovy
  sample (alignment format 2.6) and the Meridian 2 hydrography example (format 2.5, which is only told
  apart from 2.6 by content type detection). The logs must not contain known error patterns. It works
  for any built product: `./gradlew smokeTest -PsmokeTestProductDir=build/eu.esdihumboldt.hale`.

The smoke test does not start the workbench, so problems that only affect the UI are not caught.

## Problems found in OSGi and their fixes

The following problems occurred when hale»studio was first built on hale-core. They are the kinds of
problems to expect after updates of hale-core or its dependencies.

| Symptom | Cause | Fix |
|---|---|---|
| UI does not start: uses constraint violation for commons-configuration | commons-beanutils-core embeds and exports `org.apache.commons.collections`, a second exporter next to commons-collections | exclude commons-beanutils-core, unversioned import of the collections in commons-digester |
| uses constraint violation in `io.gml.ui` | hale-core contains the `io.gml.geometry` packages in two bundles | `io.gml.ui` takes them only through `Require-Bundle` of io.gml |
| `NoClassDefFoundError: javax/annotation/PostConstruct`, the workbench does not start | the e4 import is wired to jsr305, which splits `javax.annotation` with the Common Annotations API | one merged bundle exporting both versions |
| logging falls back to NOP; "Source is no valid project file" (JAXB not found); Help › Examples empty | ServiceLoader lookups across bundles | SPI Fly, configured per library |
| "Cache initialization failed … SimpleTemplateScript1", failing Groovy templates | classes compiled by Groovy at runtime cannot see `org.codehaus.groovy.runtime.*` | `DynamicImport-Package` of the Groovy packages on the bundles compiling Groovy |
| "Could not create content describer", no provider for loading the alignment | classes only named in plugin.xml or Castor mappings are not imported (invisible to bnd) | optional imports of their packages |
| SPI Fly weaving hook fails and disables the mediation | `deegree-core-coverage` (unused) references `org.ehcache`, which has no exporter | exclude it, add `deegree-core-geometry` explicitly |
| "No such property: p for class DefaultInstance" in Groovy scripts | hale's meta class fragment is part of no hale-core feature | add `eu.esdihumboldt.util.groovy.meta.fragment` to the platform |
| Tycho: logback "could not be found" | an older Eclipse used by the p2 publisher dropped bundles | pinned publisher Eclipse |

The following problems occurred with the move to Eclipse 2026-09:

| Symptom | Cause | Fix |
|---|---|---|
| "Could not create content describer", the transformations create no instances | the XML content describers of hale-core call `org.eclipse.core.internal.content.Activator`, which no longer exists | fragment `eu.esdihumboldt.hale.ui.contenttype.compat` provides a stand-in (hale-core workaround) |
| the alignment of a project cannot be loaded (JAXB runtime not found) | `org.eclipse.jdt.core.compiler.batch` exports `META-INF.services`; bundles with `DynamicImport-Package: *` wire it and no longer see their own service files | resolver hook `eu.esdihumboldt.hale.ui.resolver.hook` at start level 1 |
| the non-OSGi registry of hale-core cannot be installed | its import range of `org.osgi.framework` excludes OSGi R8 | wider import range (hale-core workaround) |
| Groovy bundles are not compiled ("signer information does not match") | unsigned copies of Eclipse classes in groovy-eclipse-batch clash with the signed Eclipse bundles | compiler in its own process (`fork`) |
| mapping views show only the connections, the nodes are invisible | `CGraphNode` of GEF Classic does not pass text and style to its figure, hale's figures get no text and no border | `CustomFigureGraphViewer` creates `CustomFigureGraphNode`s, which update their figure like the nodes of Zest 2 |
| Infocenter: topics and table of contents return 404 | the help servlets are DS components and Felix SCR was not started | start `org.apache.felix.scr` |

## Building

```
cd build
./build.sh product HALE                  # generates the platform if needed, then builds the product
./build.sh commitStage                   # test product, unit tests, smoke test
./gradlew generatePlatform [-PforceGeneratePlatform]
./gradlew smokeTest -PsmokeTestProductDir=build/eu.esdihumboldt.hale
```

On hosts that bnd-platform 3.2.1 does not know (e.g. Linux on aarch64), applying the plugin fails.
Build bnd-platform with support for them, publish it to the local Maven repository and pass its
version with `-PbndPlatformVersion=<version>` to Gradle, or with the environment variable
`ORG_GRADLE_PROJECT_bndPlatformVersion` to `build.sh`. There is no JRE for aarch64 products, so
`commitStage` fails there; run the smoke test on the product instead.

Tycho only recompiles a bundle if its sources changed. After a change of the target platform, remove
the `target` folders of the bundles to get a clean build.

## Updating hale-core

1. Renovate proposes updates of the hale-core BOM (`haleCoreVersion`). Updates under
   `build/platform/` use `fix:` commits, as they change the product.
2. CI regenerates the platform, because the version change also changes the fingerprint, builds
   the test product and runs the unit tests and the smoke test.
3. If the platform does not resolve or the product shows problems, fix the platform configuration in
   the same PR: bnd instructions for new or changed libraries, the SPI Fly lists for new ServiceLoader
   users, excludes for duplicate exporters (see "Problems found in OSGi and their fixes"). The smoke
   test does not detect every problem, so also check the logs in `build/build/smokeTest/`.
4. Remove workarounds for hale-core bundles that the new release makes unnecessary.
